# go-backend-template：这 17 篇文档怎么读

这个目录有 17 篇文档，把 `go-backend-template` 里的机制逐个拆开讲：只依赖标准库的 Go 服务骨架、版本化的 Spec 工作流、Claude Code 与 Codex 共读的行为准则、`make check` 与 `spec-check` 门禁、六个 Skill、两个 Subagent、一条 Hook，以及可选的 `spec-graph` 状态图。

每篇只回答一个问题。文里提到的落点都能在模板仓库里打开核对，例证取自 `1.0.0` 演示版本的真实运行结果。「总览」给全景，其余各篇各展开一个落点，互相引用时直接写篇名。

模板 module 是 `example.com/go-backend-template`，`go.mod` 声明 `go 1.25.0`，第三方依赖为零。复制成业务工程后第一件要做的事是换掉 module 名，Skill `init-project` 带脚本 `.ai/skills/init-project/rename_module.sh` 做这件事。

## 谁维护哪份文件

翻文档之前先分清所有权，否则很容易改错地方。

`Specs/requirements/` 归人：`需求模版.md`、`协议与数据.md`，加上每个版本一份 `需求.md`。Agent 只读这一侧。

`Specs/technical/` 归 AI：`技术讲解.md`、`技术方案模版.md`，加上每个版本一份 `技术方案.md`，启用 Graph 时还有 `graph.json`。

行为准则只有一份源文件 `.ai/ai-rules.md`。`CLAUDE.md` 与 `AGENTS.md` 指向它，`.claude/skills` 和 `.agents/skills` 都是指向 `../.ai/skills` 的符号链接。两个 Agent 读的是同一份内容。

## 按角色的阅读顺序

五种进入方式。顺序里的每一项都是篇名，在本目录找同名文件即可。

| 角色 | 目标 | 建议顺序 |
| --- | --- | --- |
| 初次接手 | 弄清模板守住了什么、谁在守、`1.0.0` 为什么停在 `verifying` | 总览 -> Rules 落地 -> Spec 落地 -> 版本开发工作流 -> 验证闭环 -> Command 落地 -> 工程骨架 |
| 新建业务工程 | 用 `init-project` 从模板复制出工程，再按七个 Step 做第一个版本 | Skill 落地 -> 工程骨架 -> 代码规范与日常修改 -> spec-init -> 版本开发工作流 -> API 契约设计 -> 测试分层 -> 验证闭环 |
| 接入存量工程 | 用 `spec-coding-init` 给已有 Go 工程补上 Specs 目录、行为准则与门禁 | Skill 落地 -> Rules 落地 -> Spec 落地 -> Command 落地 -> 第三方 Skill -> MCP 落地 -> Subagent 与 Hook 落地 |

| 启用 Graph | 理解证据失效判定，再用 `spec-graph` CLI 与 Subagent 编排一个版本 | Spec + Graph 理论 -> Spec + Graph 落地 -> Subagent 与 Hook 落地 -> 验证闭环 -> spec-init -> 代码规范与日常修改 |

## 1.0.0 停在 verifying

演示版本 `1.0.0` 实现了两个接口，`POST /v1/notes` 和 `GET /v1/notes/{id}`，数据只在进程内存里。门禁、冒烟、`api-verify` 与两轮独立审查都跑完了，`Specs/technical/1.0.0/技术方案.md` 的交付状态块仍写着：

```yaml
stage: verifying
user_acceptance: pending
review: pass
```

`spec-check` 接受这个组合。它只在 `stage: delivered` 时要求 `user_acceptance: confirmed` 且 `review` 为 `pass` 或 `not_required`。命令能证明的到这里为止：当前候选通过了全部确定性检查。用户接不接受这个行为，命令答不了。

| 命令 | 结果 |
|---|---|
| `make check` | 通过；`spec-check ok (1 version(s))` |
| `make test-integration` | 通过 |
| `make test-race` | 通过 |
| `make smoke` | 九项全部 `OK`，`smoke passed` |
| `make lint` / `make vuln` | golangci-lint / govulncheck 未安装，按设计跳过 |
| Skill `api-verify`（端口 18090） | 17 项场景通过，服务器日志不含笔记正文 |
| Subagent `spec-reviewer` | 第一轮 `changes_required` 5 条 finding，修复后第二轮 `pass`，新增 R6 由 Controller 修正，6 条全部 verified |
| `go run ./cmd/spec-graph check 1.0.0` | 退出码 0 |

「验证闭环」讲这道停止线为什么存在，「Command 落地」讲每条命令各自守什么。

## 先跑命令，再信文档

接手模板的第一件事是重跑门禁，而不是读完 17 篇。四条命令覆盖必需检查的全部范围：

```sh
make check              # vet + go test ./... + spec-check + gofmt 检查
make test-integration   # 带 integration 标签的用例
make test-race          # 竞态检测
make smoke              # 起真实二进制，按契约打九项
```

`make lint` 与 `make vuln` 是可选目标。golangci-lint 与 govulncheck 未安装时打印提示后跳过，不影响退出码。`make spec-init VERSION=x.y.z` 缺 `VERSION` 时打印用法并以 2 退出。`Makefile` 一共十四个目标，逐条解释在「Command 落地」。

## 模板内的两份速查

`docs/spec-graph/理论.md` 与 `docs/spec-graph/落地.md` 是「Spec + Graph 理论」和「Spec + Graph 落地」在工程内的速查版本。两边对不上时以模板内文件为准。

# Memory：跨会话该把什么留在文件里

## 概念

每开一个新会话，模型是空的。上一轮花两小时排查出的结论、被推翻的假设、需要人反复提醒才没走错的那一步，全都不会自动带过来。第二天接着做同一个功能，它会重新做一遍同样的判断，也可能重新踩一遍同样的坑。

所谓 memory 不是模型的能力，是把该被继承的事实写进文件、并让新会话第一时间读到。载体是文件，触发是读取顺序，两者缺一都不成立——写得再全，新会话不读也等于没有。

该被继承的东西分三类，更新频率和维护者都不一样：

| 类型 | 内容 | 谁维护 | 什么时候变 |
| --- | --- | --- | --- |
| 长期约束 | 权限边界、工作流、代码规范、验证命令 | 人与 AI 共同演进 | 极少，规则本身改变时 |
| 技术全景 | 目录结构、模块职责、接口清单、配置、已知问题 | AI | 代码结构变化时 |
| 过程记录 | 某个版本的决定、变更、交付状态 | AI | 版本推进时 |

三类之外还有第四类，也是最容易丢的一类：跨版本、跨会话的经验。它不属于任何一个版本，也不该塞进规则正文——「某个环境变量在 CI 里拿不到默认值」「以为 `DisallowUnknownFields` 能拦住类型错误，实测拦不住」这种，写进规则会把正文撑到没人读，不写下来下个会话必然重来。

判断一条信息该不该留下，只问一个问题：新会话不知道这件事会怎样。答案是「读一遍代码就知道」的，不写；答案是「会重新做一次错误判断」的，写。

## 本工程怎么落地

四层分工，各有单一载体：

| 层 | 文件 | 内容 |
| --- | --- | --- |
| 长期约束 | `.ai/ai-rules.md` | 文件权限、能力前置校验、Step 1 到 Step 7、代码规范、验证命令 |
| 跨会话经验 | `.ai/memory.md` | 已验证的事实、踩过的坑、待验证 |
| 技术全景 | `Specs/technical/技术讲解.md` | 目录结构、核心模块、接口清单、测试策略、已知问题与待优化项 |
| 版本决定 | `Specs/technical/{version}/技术方案.md` | 「变更记录」与「交付状态」 |

第一层通过符号链接进入两个 Agent 的会话：`CLAUDE.md` 和 `AGENTS.md` 都指向 `.ai/ai-rules.md`，两边读到同一段字节。

`.ai/memory.md` 的结构固定为三节，标题不能改：

- **已验证的事实** — 非显然、且被命令或测试证实过的结论，每条注明被什么验证
- **踩过的坑** — 真实发生过的错误，写清代价和下次怎么避免
- **待验证** — 有依据但还没跑过的判断，验证后移到前两节，被推翻就删掉并在「踩过的坑」补一条

「每条注明被什么验证」是这份文件和普通笔记的分界。没有验证来源的条目无法判断是否过期，也无法在被推翻时定位到该改哪一条。

文件本身带引导头，写明新会话该从哪拿什么：

> 新会话读 `.ai/ai-rules.md` 拿长期约束，读 `Specs/technical/技术讲解.md` 拿技术全景，读这里拿上一轮踩过什么坑、验证后推翻了什么假设。

三个标题由 `spec-check` 守着。`internal/speccheck/speccheck.go` 把 `.ai/memory.md` 列进 `requiredFiles`，缺文件报「缺少必需文件」；`memoryHeadings` 定义三个标题，由 `checkHeadings` 逐行核对，围栏代码块内的行不计数。`memory.md` 的 `exactlyOnce` 传 `false`，所以重复标题不报错，只有缺失才报。`speccheck_test.go` 的 `TestRun_MemoryHeadings` 对三个标题各做一次改名反例，外加一个把三行全塞进围栏代码块的用例，验证围栏内确实不算数。

写入时机固定两处，不靠自觉：

- **Step 7 第 8 项** — 本版本如果出现了被验证推翻的假设、靠人反复提醒才没做错的步骤，或验证后确认的非显然事实，各记一条；没有就不写
- **日常代码修改第 6 项** — 修复过程中推翻了原先的判断，或发现一个不看代码就会重复踩的坑，记一条

准则的「持续学习」一节给出边界。不写的东西：进度、待办、临时讨论、还没验证的猜测、密钥，以及读代码就能直接看出来的事实。理由写在同一节里——记忆文件长到没人读，就失去作用。条目过期时直接删除或改写，不保留互相矛盾的两条。

「一条都没有就不写，不要为了填充而编」是必要的一句。没有这句，Step 7 会变成每个版本例行产出三条正确但无用的废话，几个版本后这份文件就没人看了。模板自带的 `memory.md` 三节内容都是「暂无」，从模板复制出的工程从零开始记。

版本级的决定不进 `memory.md`。技术方案的「变更记录」记本版本改了什么、为什么改，「交付状态」用 `stage` / `user_acceptance` / `review` 三个键记录用户决定，`spec-check` 会拒绝 `user_acceptance` 未 `confirmed` 的 `delivered`。这两块随版本目录留存，不需要跨版本继承。

## 扩展思路

**条目多了先分组，再拆文件，但入口只留一份。** 三节之内按主题加三级标题是第一步；真到要拆成 `.ai/memory/{topic}.md` 时，`memory.md` 只留索引和跨主题的坑，同时把新文件加进 `requiredFiles`——否则某个主题文件被删掉不会有任何东西报错。

**团队级经验和项目级经验分开。** `sync-ai-assets` 同步 Skills、`.ai/ai-rules.md`、Specs 模版、配置与脚本、符号链接，以及 `spec-check` / `spec-graph` 这类工具包代码，唯独不含 `memory.md`，所以模板更新不会把别的项目的坑带过来。反过来，一条经验如果对所有从模板起步的工程都成立，它的位置就不是 `memory.md`，而是准则正文或某个 Skill 的 references——放错地方的结果是每个工程各自重新发现一遍。

**给条目加来源。** 除了「被什么验证」，再加上「哪个版本、哪次验证」。半年后清理时，能直接判断某条是否还对应现存代码；找不到对应版本的条目多半已经过期。

**反复解释的背景不进记忆文件。** 业务背景、领域术语、状态机的合法迁移，这类东西每次会话都要用，属于长期知识：对外契约进 `Specs/requirements/协议与数据.md`，模块与数据的组织方式进 `技术讲解.md`。塞进 `memory.md` 的结果是它变成第二份技术文档，然后和第一份分叉。

**记忆条目和规则冲突时以规则为准。** 冲突本身是个信号：要么这条经验已经过期，删掉；要么它稳定到该升级——写进 `.ai/ai-rules.md` 成为规则，或者干脆变成 `spec-check` 的一条断言。一条经验被重复触发三次以上还只躺在 `memory.md` 里，说明它选错了载体。判断依据和写规则时一样：这件事如果没人记得，多久会被发现？答案是「下个会话就会重犯」的，就该往上升一层。

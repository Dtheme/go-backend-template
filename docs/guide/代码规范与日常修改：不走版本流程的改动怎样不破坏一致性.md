# 代码规范与日常修改：不走版本流程的改动怎样不破坏一致性

把 `SHUTDOWN_TIMEOUT` 的默认值从 `10s` 改成别的数。修一个 404 message 的错字。这类改动写不出一份新需求，也不值得走完七个 Step，可它们照样会碰到技术讲解、Postman 集合、冒烟脚本，以及 `graph.json` 里已经记录的证据。

模板给的答案不是「小改动随便改」。`.ai/ai-rules.md` 单列了「日常代码修改（非版本开发）」五步，另把「代码规范」写成九节硬约束。版本流程管的是要做什么、谁来确认。五步和九节管另一件事：改动无论大小，怎么改才不会让仓库里其他事实失效。

## 日常修改和版本开发的分界在哪里

区别不在改动行数，在有没有外部行为需要人来拍板。版本开发从 `Specs/requirements/{version}/需求.md` 出发，要过技术方案确认、6.2 用户验证和 Step 7 回写。日常修改只处理 bug 修复、小优化和配置调整，没有方案确认关口，也不碰「交付状态」块。

| 维度 | 版本开发（Step 1 到 Step 7） | 日常代码修改（五步） |
| --- | --- | --- |
| 触发 | 人工需求里的新功能或需求变更 | bug 修复、小优化、配置调整 |
| 设计文档 | `make spec-init` 生成技术方案，用户确认后才编码 | 不生成技术方案，先读 `Specs/technical/技术讲解.md` |
| 用户参与 | 方案确认与 6.2 用户验证两道关口 | 无确认关口 |
| 必跑门禁 | `make check`、`make test-integration`、`make smoke`、`api-verify` 必跑；`make test-race` 在涉及并发改动时执行 | `make check` 必跑，其余按触及范围补跑 |
| 状态记录 | 技术方案「交付状态」块，启用 Graph 时还有 `graph.json` | 不改交付状态，只回写受影响的文档 |

五步原文如下（`.ai/ai-rules.md`「日常代码修改（非版本开发）」）：

```text
1. 修改前读取 Specs/technical/技术讲解.md 了解相关模块；涉及接口时再读 协议与数据.md
2. 先写复现问题的失败测试（单元或集成），再修复
3. 修改后跑 make check；触及外部依赖时跑 make test-integration；接口行为有变化时再跑 make smoke 和 api-verify 对应接口
4. 更新 技术讲解.md（改动影响技术全景时）；涉及某版本功能时同步对应 技术方案.md；接口变化同步 Postman 集合
5. 涉及新增包、公共函数或成段新代码时，动手前先扫现有公共实现，遵循 DRY 红线
```

五步里没有「改需求」这一项。`Specs/requirements/**` 对 AI 只读，日常修改只能让代码向既有契约靠拢，反过来不行。6.3 第 5 条写明用户反馈属于新增需求或需求变更时按「需求变更与新增规则」处理，不得当作 bug 直接改。日常修改套用同一条判断：改动只要让 `协议与数据.md` 或某版本需求里写明的行为发生变化，它就不再是日常修改。信息所有权落到小改动上，就长这样。

启用 `spec-graph` 还多一层机器判断。candidate 摘要覆盖 `cmd`、`internal`、`scripts`、`api`、`migrations` 下的普通文件加 `go.mod`、`go.sum`、`Makefile`；阶段处于 `reviewing`、`verifying` 或 `ready_to_deliver` 时，任何让摘要变化的改动都会让 `status` 派生出 `invalidated: true`。1.0.0 停在 `verifying`、revision 46、`invalidated` 为 false，最终门禁记录（revision 42 到 46）绑定候选 `2d03ec4f1c56`。改 `internal/httpapi/notes.go` 一行，`verified` 守卫里的 `boundEvidence` 就会报告证据绑定的 candidate 与当前不一致，得先执行 `event 1.0.0 readiness_invalidated` 回到 `fixing`。日常修改不写 `graph.json`，却会让 Graph 里已有的结论失效。Loop 管局部收敛，Graph 管结论是否仍然有效，分工在这条线上。

## 规范九节各自守住什么

九节里每一节都能在当前代码里找到落点。它约束的是 `cmd -> httpapi -> note <- memstore` 这条依赖方向、统一错误信封和三层测试，让它们在下一次改动后仍然成立，不是一份风格偏好清单。

| 节 | 核心约束 | 当前代码里的落点 |
| --- | --- | --- |
| 包组织与依赖方向 | `cmd` 只装配；`httpapi` 不访问存储；领域包不 import `net/http` 和存储驱动；反向 import 视为设计错误；不预置空目录和无调用方的抽象 | `cmd/api/main.go` 只创建 logger、`config.Load()`、`memstore.New()`、`note.NewService` 和 `http.Server`；`internal/note/note.go` 只 import 标准库；`internal/memstore/store.go` 除标准库外只 import `note` |
| 命名 | 导出类型不重复包名；接口按行为命名；`ErrXxx` 与 `XxxError`；测试 `TestXxx_场景` | `note.Service`、`memstore.Store`、`note.Repository`、`ErrNotFound`、`ErrAlreadyExists`、`ValidationError`、`TestCreateNote_BadBody` |
| 错误处理 | `fmt.Errorf("动作: %w", err)` 包装；领域层定义业务错误，HTTP 层集中映射；未预期错误 500 `internal_error`；`_ = err` 只允许 `writeJSON` 里的 `Encode` | `note.go` 的 `save note: %w`；`notes.go` 的 `writeServiceError`；`response.go` 第 20 行 |
| HTTP 层 | `METHOD /path` 注册；`r.PathValue`；`DisallowUnknownFields` 加 `http.MaxBytesReader`；响应只经 `writeJSON` / `writeError`；上下文走 `r.Context()` | `handler.go` 的 `POST /v1/notes` 与 `GET /v1/notes/{id}`；`notes.go` 的 `decodeJSON` 与 `r.PathValue("id")` |
| 并发与资源 | goroutine 必须有退出路径；锁范围最小且持锁不做 I/O；资源在 `cmd` 创建并在 `Shutdown` 关闭；并发改动跑 `go test -race` | `main.go` 的 `errCh` 与信号 `select`、`server.Shutdown(ctx)`；`memstore.Store` 的 `sync.RWMutex` 只包住 map 操作；`make test-race` 即 `go test -race ./...` |
| 日志与配置 | 只用 `log/slog`；不记密码、token、完整请求体；配置只来自环境变量并集中在 `internal/config` | `main.go` 的 `slog.NewJSONHandler`；请求日志只有 `method`、`path`、`status`、`duration_ms`；`config.Load` 解析 `HTTP_ADDR` 与 `SHUTDOWN_TIMEOUT`，非法时长回退默认 |
| 测试 | 无 tag 单元、`//go:build integration` 集成、按需 `e2e`；同包表驱动；自建 fixture 并 `t.Cleanup`；每条验收标准至少一个测试；deterministic 默认 `count=1` | `helpers_test.go` 无标签供两层共用；`integration_test.go` 首行 `//go:build integration`；`TestIntegration_HealthzAndPing` 用 `t.Cleanup(srv.Close)` |
| DRY 红线 | 约 3 行以上逻辑出现第二处前先抽；多个 `switch` 改映射表；1 处调用点先留在使用处；4 个以上参数或多个布尔开关说明不该抽 | 「当前公共实现清单」三行；`toNoteResponse` 被 `create` 与 `get` 共用 |
| 依赖使用 | 标准库优先；新增第三方依赖前告知用途、替代方案、许可证、维护状态；`go.sum` 入库 | `go.mod` 只有 module 声明与 `go 1.25.0`，没有 require 块 |

错误处理一节最能说明「集中」是什么意思。领域层定义 `ErrNotFound`、`ErrAlreadyExists` 和 `ValidationError`。HTTP 层只显式映射 `ErrNotFound` 与 `ValidationError`，`ErrAlreadyExists` 落进 default 分支返回 500 `internal_error`。状态码与 `error.code` 的对应关系只写在 `internal/httpapi/notes.go` 一个地方：

```go
func (h *notesHandler) writeServiceError(w http.ResponseWriter, r *http.Request, err error) {
	var ve *note.ValidationError
	switch {
	case errors.As(err, &ve):
		writeError(w, http.StatusBadRequest, "invalid_argument", ve.Message)
	case errors.Is(err, note.ErrNotFound):
		writeError(w, http.StatusNotFound, "not_found", "note not found")
	default:
		h.logger.Error("note request failed", "method", r.Method, "path", r.URL.Path, "error", err)
		writeError(w, http.StatusInternalServerError, "internal_error", "internal server error")
	}
}
```

`TestNotes_RepositoryFailureReturns500` 用一个返回 `disk on fire` 的 `failingRepo` 验证 500 响应的 `error.message` 不带内部细节，「响应不泄露内部信息」被这条测试钉住了。「不记录完整请求体」没这个待遇。仓库里没有测试断言日志内容，`helpers_test.go` 的 `testLogger` 把日志写进 `io.Discard`，唯一的核对是 api-verify 实录里的一次日志检查，而 6.1 写明手动 curl 或 Postman 通过但没有对应测试的行为不算已验证。日志与配置一节的这一半靠执行者自觉。

## 公共实现清单是一份要回填的账

Step 5 要求动手前扫一遍 `internal/httpapi/response.go` 和各领域包的端口接口，日常五步第 5 条指向同一份清单。`.ai/ai-rules.md` 当前登记的公共实现只有三行：

| 需求 | 优先用 | 不要这么干 |
| --- | --- | --- |
| JSON 响应 / 错误响应 | `httpapi.writeJSON`、`httpapi.writeError` | handler 里手写 `w.Header().Set` + `json.Marshal` |
| 请求日志 / panic 兜底 | `httpapi.withRequestLog`、`httpapi.withRecover` | 各 handler 各自 `defer recover()` 或打印日志 |
| 环境变量配置 | `config.Load` | 业务包里直接 `os.Getenv` |

清单归项目自己维护。`sync-ai-assets` 同步行为准则时默认保留本项目的「当前公共实现清单」，`spec-coding-init` 改造存量工程时按扫描到的公共函数填写。没有任何机器会替它更新。回填是写代码的人的义务。

1.0.0 新增的 `decodeJSON` 就是一个待回填项，它在 `internal/httpapi/notes.go` 里：

```go
func decodeJSON(w http.ResponseWriter, r *http.Request, dst any) error {
	r.Body = http.MaxBytesReader(w, r.Body, maxBodyBytes)
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	if err := dec.Decode(dst); err != nil {
		return err
	}
	if err := dec.Decode(&struct{}{}); !errors.Is(err, io.EOF) {
		return errors.New("request body must contain a single JSON value")
	}
	return nil
}
```

`decodeJSON` 目前只有 `notesHandler.create` 一个调用点，按「1 处调用点先写在使用处」似乎可以不登记。那条规则针对的是要不要抽公共件，而 `decodeJSON` 已经以 `dst any` 的形式写成了通用函数，剩下的问题只是下一个带请求体的 handler 能不能找到它。三点事实支持回填。它放在 `notes.go`，不在 Step 5 点名扫描的 `response.go`，按规则扫描根本看不到。「HTTP 层」一节只写了 `DisallowUnknownFields` 和 `http.MaxBytesReader`，没提尾随数据，照规则重写一遍就会把审查 finding R2 修掉的缺陷带回来。`maxBodyBytes` 的 16 KiB 上限与它绑定，第二份实现很容易换个数字。该做的是在表里加一行「JSON 请求体解析 | `httpapi.decodeJSON` | handler 里自己 `json.NewDecoder` + `DisallowUnknownFields`」。至于把函数搬进 `response.go`，那是一次机械搬迁，等第二个调用点出现再做。

按当前文件，这一行还没写进 `.ai/ai-rules.md`。1.0.0 停在 `verifying`，Step 7 尚未执行，而 Step 7 的七项回写清单里也没点名 `ai-rules.md` 的公共实现清单。「新增后回填」最容易漏在这个位置。

## 什么时候该抽象，什么时候不该

模板里的例子分两组。该抽的一组都有第二个调用点或一个变化原因：`writeJSON` 与 `writeError` 被 `handler.go`、`notes.go`、`middleware.go` 三个文件使用；`toNoteResponse` 在 `create` 与 `get` 各用一次，符合「准备出现第二处时先抽」；错误映射只在 `writeServiceError` 一处，等将来第二个领域出现再按「多处 `switch` 改映射表」升级。

不该抽的一组同样有据可查：

- `note.Service` 用 `now func() time.Time` 和 `newID func() (string, error)` 两个函数字段做测试接缝，没为它们定义时钟或 ID 生成器接口；`TestService_Create_IDGenerationFails` 替换字段就能覆盖失败路径。
- `cmd/api/main.go` 直接装配，没有 Factory 或 Container；`internal/memstore` 与 `internal/config` 各只有一个类型，各只有一个非测试文件。
- 404 / 405 仍由 `ServeMux` 返回纯文本。技术讲解把它记在「已知问题与待优化项」，写明需要统一时再在 `NewHandler` 中包一层 fallback handler，不提前预置。

停止信号也写得很具体：抽象后需要 4 个以上参数或多个布尔开关，说明不该抽，在方案里写明理由保留重复。「包组织与依赖方向」一节是同一个意思：不为「将来可能需要」创建 Manager / Service / Factory 等无调用方的抽象，一个包只有一个类型时不单独拆文件。

## 修改之后怎样知道一致性没有被破坏

第一道是 `make check`。Makefile 里它是 `vet test spec-check` 加一行 `gofmt -l` 非空即失败。门禁实录中 `make check`、`make test-integration`、`make test-race`、`make smoke` 全部通过，`spec-check` 输出 `spec-check ok (1 version(s))`，`make lint` 与 `make vuln` 因工具未安装按设计跳过。

第二道是编辑后的即时反馈。`.claude/settings.json` 的 `PostToolUse` 以 `Edit|Write` 匹配并调用 `scripts/check-format.sh`，脚本行为已用探针验证。真实 Claude Code 会话中的自动触发尚未记录，Codex 没有对应机制，格式检查最终仍然落回 `make check`。Hook 是事后反馈，撤销不了已经写入的内容，也不覆盖 Bash 产生的改动。探针结果与边界见「Subagent 与 Hook 落地」。

第三道没有机器。`spec-check` 十条规则只核对技术讲解有没有「目录结构」「接口清单」「测试策略」「已知问题与待优化项」四节，判断不了内容是否过时。1.0.0 审查中的 R5，技术讲解与 README 落后于代码，是 `spec-reviewer` 读出来的，不是命令跑出来的。日常五步第 4 条只能靠执行者自觉。技术讲解文件头也写明版本开发结束和日常修改后都要更新它。

绿色不等于交付，也不等于一致。日常修改的完成标准是：失败测试先出现再消失，`make check` 通过，技术讲解、技术方案、Postman 集合中受影响的部分已经改过，新增的公共函数已经登记，启用 Graph 时知道哪些证据因此失效。少一项，仓库里就多一处与代码不符的事实，下一个会话会把它当真。

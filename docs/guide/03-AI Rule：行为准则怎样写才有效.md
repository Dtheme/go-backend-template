# AI Rule：行为准则怎样写才有效

## 概念

大多数行为准则写成了提醒：「注意代码质量」「测试要充分」「不要修改需求文档」。这类句子读起来没错，模型也确实读到了，但它不改变任何一次具体的工具调用——因为句子里没有动作，没有对象，也没有失败后果。

有效的准则满足三个条件。

**能落到动作**。一条规则要说清「在什么时机、对哪个路径、执行哪个命令、失败了做什么」。「测试要充分」落不到动作；「每个业务规则先写失败测试，确认失败原因正确，再写最小实现」可以，因为它规定了顺序和可观察的中间态。「注意 Go 版本」落不到动作；「`go version` 输出低于 go.mod 声明就 STOP，提示用户切换版本」可以。

**有唯一来源**。同一条约束出现在两个文件里，就会在某次修改后分叉，之后无法判断哪份是对的。Claude Code 读 `CLAUDE.md`，Codex 读 `AGENTS.md`，Skills 目录两边路径也不同——如果各写一份，第三次改动就开始漂移。正确做法是一份正文，其余全是链接。

**能被机器核对**。写下的规则如果没有任何程序检查它是否还在，它就只是建议。有人删掉「文件权限规则」一节，或者把符号链接改成了复制的普通文件，仓库照样能编译、测试照样通过，问题要到几周后 AI 改错了需求文档才暴露。检查器的作用是让这类退化在提交前就失败。

## 本工程怎么落地

准则正文只有一份：`.ai/ai-rules.md`。仓库根的两个准则入口指向它，两个 Agent 各自的 Skills 目录指向同一份实体，四条都是符号链接：

```
CLAUDE.md      -> .ai/ai-rules.md
AGENTS.md      -> .ai/ai-rules.md
.claude/skills -> ../.ai/skills
.agents/skills -> ../.ai/skills
```

两个 Agent 读到的是同一段字节，Skills 目录也是同一份实体。`.codex/config.toml` 里只写与 Claude Code 的差异（Codex 没有 Hook 和 Subagent，格式检查依赖 `make check`，独立审查在新会话中按 `.claude/agents/spec-reviewer.md` 正文执行），不重复准则内容。

准则正文按约束对象分节，每节管的东西互不重叠：

| 节 | 约束什么 |
| --- | --- |
| 文件权限规则 | 逐条路径的读写权限，如 `Specs/requirements/**` AI 禁止修改，`Specs/technical/{version}/graph.json` 只能通过 `spec-graph` 命令写入 |
| 能力前置校验 | 动手前确认 Go 工具链、make、curl、Skill 等能力可用，缺失时的处理 |
| AI 工作流（版本开发） | Step 1 到 Step 7 的完整版本闭环，含需求变更时必须回到「更新技术方案 -> 用户确认 -> 编码 -> 维护文档」 |
| 日常代码修改 | bug 修复、小优化不走完整流程时的最小要求：先读技术讲解、先写失败测试、跑 `make check` |
| 代码规范 | 包组织与依赖方向、命名、错误处理、HTTP 层、并发与资源、日志与配置、测试分层、DRY 红线、依赖使用 |
| 验证命令 | 每条命令跑什么、何时跑、必需还是可选 |
| Skills | 6 个 Skill 各自的用途与触发时机，调用方式 `/{skill}` 与 `${skill}` |
| Subagent 与 Hook | `spec-reviewer`、`spec-implementer`、`PostToolUse` Hook 的作用与边界 |

「代码规范」的写法值得单看：它不写「遵循 Go 最佳实践」，而是写「依赖方向只允许 `cmd -> httpapi -> domain <- storage`；出现反向 import 视为设计错误」，写「响应只通过 `writeJSON` / `writeError`，不手写 `w.Write`」。DRY 红线一节直接给出当前公共实现清单表格，三列是「需求 / 优先用 / 不要这么干」，新增公共件后回填。这样写出来的规则，AI 在具体某行代码上能判断自己有没有违反。

守规则的是 `cmd/spec-check`，它是 `make check` 的一部分。`internal/speccheck/speccheck.go` 里两个变量定义了准则相关的硬约束：

- `rulesHeadings` — `## 文件权限规则`、`## AI 工作流（版本开发）`、`## 验证命令` 三节标题必须各出现一次
- `requiredSymlinks` — 上面四条链接的目标必须逐字匹配，且目标要真实存在

标题检查由 `checkHeadings` 完成，`exactlyOnce` 为 `true` 时重复出现也算问题，围栏代码块（``` 或 ~~~）内的行不计数，避免目录树示例里的字符串被误判。链接检查用 `os.Lstat` 判断确实是符号链接、`os.Readlink` 比对目标、再 `os.Stat` 确认目标可达——普通文件、指错、指向不存在的路径是三条不同的报错。

退出码在 `cmd/spec-check/main.go`：0 表示无问题，1 表示有规则违反，2 表示参数或 I/O 错误。所以准则被删节或链接被改成副本时，`make check` 直接红。

准则里的「能力前置校验」用分级替代了一刀切。表格三列是「能力 / 探针 / 缺失时」，分两类：

- 必需：Go 工具链、make、curl、Skill。校验失败必须 STOP，明确告知缺什么、怎么装，不得绕过或用其他方式凑合
- 可选：git、Postman MCP、golangci-lint / govulncheck。缺失时说明改用的替代方式即可，`make lint` / `make vuln` 未安装自动跳过

分级的意义在于 STOP 只用在真会导致结论失真的地方。全部必需，AI 会在缺 Postman MCP 时停下等待；全部可选，缺 Go 工具链时它会试图靠读代码「推断」测试结果。「能力前置校验」末尾那句「本工程的必需门禁不依赖任何 MCP Server」是这条分级的兜底。

## 扩展思路

业务工程接手后，往准则里加的应该是「AI 猜不到、猜错了代价高」的东西。

**技术选型边界**。哪些库已选定、哪些禁止引入、哪些需要先问。模板里已有一条「标准库优先，新增第三方依赖前告知用户：用途、替代方案、许可证、维护状态」，业务工程可以把它具体化成清单——ORM 用哪个、日志库是否允许替换 `log/slog`、HTTP 框架是否允许引入。

**发布约定**。分支命名、tag 格式、CHANGELOG 写法、灰度与回滚步骤、谁有权限执行。这类知识分散在人脑里时，AI 每次都会重新发明一套。

**领域术语**。业务里「订单」「工单」「履约单」的准确边界，状态机的合法迁移，哪些字段对外可见。写进准则后，AI 生成的类型名和错误码会稳定得多。

规则条数上去以后，一份正文会开始变难读。两条出路：按领域拆成 `.ai/rules/{domain}.md`，正文只留索引和跨领域约束；或者把低频规则移进 Skill，由触发描述决定何时加载——`go-development` 的 `references/testing.md`、`architecture.md` 就是这个用法，编码时按需加载，不占常驻上下文。

**新约定要同步进 spec-check**。加了一节「## 发布流程」而没有把标题加进 `rulesHeadings`，这一节被删掉时没有任何东西会报错。加了新的共享资产目录而没有加进 `requiredSymlinks`，它被改成复制品时两个 Agent 就开始读不同的内容。判断标准很简单：这条规则如果消失了，多久会被发现？答案是「几周后」的，就该有检查。

`internal/speccheck/versions.go` 演示了检查器往深处走的样子——版本目录名必须匹配 `^[0-9]+\.[0-9]+\.[0-9]+$`，技术方案必须含 `## 需求摘要`、`## API 契约`、`## 模块设计`、`## 测试计划`、`## 风险与回滚`、`## 文件清单`、交付状态块、`## 变更记录` 八节，版本目录下只允许出现白名单内的文件名。业务工程要固化的约定越具体，越应该沿这条路加断言，而不是往正文里再加一句提醒。

**两个 Agent 的能力差异要标注在准则里**，而不是让读者自己发现。模板的做法是在「Subagent 与 Hook（Claude Code）」一节标题上直接写明适用范围，正文末尾给出 Codex 的替代路径。业务工程如果引入了只有一边支持的机制（某个 MCP、某种 Hook 时机、某类工具预授权），照同样格式补一行「另一边怎么办」，否则在 Codex 会话里执行到那一步就会卡住或静默跳过。

# 验证闭环：自验通过之后为什么还要等用户确认

`1.0.0` 演示版本上，`make check`、`make test-integration`、`make test-race`、`make smoke` 全部通过，`api-verify` 对真实进程核对了 17 个场景，`spec-reviewer` 第二轮审查返回 `pass`。按直觉，这个版本可以写成交付完成。技术方案「交付状态」块仍停在 `stage: verifying`、`user_acceptance: pending`，`go run ./cmd/spec-graph event 1.0.0 verified` 被守卫以退出码 3 拒绝。

两种验证回答的是不同问题。Agent 自验说明代码符合 Agent 自己写进技术方案的契约，每个场景都有测试固化。用户确认说明这份契约就是用户想要的行为。前者能由命令给出，后者只能由用户给出。`go-backend-template` 把这条边界写进 `.ai/ai-rules.md` 的 Step 6，用「交付状态」块把用户的决定变成 `spec-check` 能核对的事实，「自验通过」和「版本交付」在文件上就混不到一起。

## 6.1 七项自验各自证明什么

`.ai/ai-rules.md` 的 6.1 要求按顺序执行七项，全部通过才算自验完成。七项分层回答不同问题，不是把测试跑七遍（分层本身见「测试分层」）：

| 项 | 命令或动作 | 证明什么 | 1.0.0 实际结果 |
| --- | --- | --- | --- |
| 1 | `make check` | `go vet`、单元测试、gofmt 检查、`spec-check`（版本目录与 Feature ID、技术方案章节、「交付状态」块、符号链接） | 通过，`spec-check ok (1 version(s))` |
| 2 | `make test-integration` | `-tags integration` 走真实网络的请求链路；触及外部依赖时必须先备好依赖，不得跳过 | 通过 |
| 3 | `make test-race` | 本版本涉及并发改动时执行；无并发改动可说明后跳过 | 通过（内存存储与并发创建属于并发改动） |
| 4 | `make smoke` | 编译真实二进制、启动、curl 校验 | 通过，`scripts/smoke.sh` 共 9 项检查 |
| 5 | Skill `api-verify` | 按技术方案 API 契约对真实进程逐接口核对状态码、响应字段、错误信封 | 17 个场景通过 |
| 6 | 对照需求「验收标准」逐条核对 | 每条 AC 都有对应的单元或集成测试固化 | 技术方案「测试计划」已回写为实际用例名 |
| 7 | 把「交付状态」`stage` 改为 `verifying` | 声明自验结束、进入用户验证 | 已改为 `verifying` |

第 7 项是状态变更，把「Agent 认为可以交给用户看了」这个判断落到文件里。可选加强是 `make lint` 与 `make vuln`，工具已安装时执行并把结果附在报告中。本机没有装 golangci-lint 与 govulncheck，Makefile 按设计输出「未安装，跳过（可选）」，这两项缺席不影响必需门禁的结论（命令与脚本的分工见「Command 落地」）。

6.1 末尾还有一条硬规则：自验中任一项失败，修复后重新执行受影响的项，不得带着失败进入 6.2；手动 curl 或 Postman 通过但没有对应测试的行为，不算已验证。`api-verify` 就是照这条规则设计的。

## api-verify 怎样对真实进程核对契约

`.ai/skills/api-verify/SKILL.md` 把自己定位成 Step 6.1 的最后一道自验：只确认真实二进制的行为与契约一致，不替代单元测试与集成测试。前置校验先要求 `go version` 与 `curl --version` 可用，再要求 `make check` 与 `make test-integration` 已通过；没通过就回到测试，不做契约核对。然后读取验证来源：传入 version 时是该版本技术方案的「API 契约」，不传时是 `api/postman/*.postman_collection.json` 加 `技术讲解.md` 的接口清单。错误信封约定读 `Specs/requirements/协议与数据.md`。需要外部依赖时确认 `/readyz` 返回 200。Postman MCP 是可选项，存在时可以额外运行集合，没有则跳过，不影响结论（MCP 不进入必需门禁的理由见「MCP 落地」）。

执行流程编号 1 到 6 共六个 Step，Step 3 之后插入一个 Step 3.5。Step 1 启动服务的写法固定：

```bash
# .ai/skills/api-verify/SKILL.md
PORT="${API_VERIFY_PORT:-18090}"   # 与 scripts/smoke.sh 的 18080 错开；被占用时换一个未使用端口
RUN_DIR="$(mktemp -d)"             # 每次运行独立目录，多次并行不会互相覆盖或误杀
go build -o "$RUN_DIR/api" ./cmd/api
HTTP_ADDR=":$PORT" "$RUN_DIR/api" > "$RUN_DIR/server.log" 2>&1 &
echo $! > "$RUN_DIR/pid"
for i in $(seq 1 50); do curl -fs "http://127.0.0.1:$PORT/healthz" >/dev/null && break; sleep 0.1; done
```

`mktemp -d` 让二进制、日志和 pid 文件都落在一次性目录里。端口 18090 与冒烟脚本的 18080 错开，两者同时运行不会互相误杀。

Step 2 对契约中的每个接口至少覆盖四类：成功路径、每种错误场景、方法不匹配（确认 405）、契约声明时的幂等或重复提交。Step 3 核对 Postman 集合，缺请求记「集合待补」，与契约不一致记「集合待更新」；MCP 断言失败而 curl 通过时判定为集合过期，不是接口失败。Step 3.5 对 Step 2 的每个场景在 `*_test.go` 或 `*_integration_test.go` 中找到对应用例名，找不到记为「缺测试」，必须在 Step 6 补齐后才能给出「通过」。Step 4 无论结果如何都 `kill` 进程、`rm -rf "$RUN_DIR"`，并用 `lsof -i :$PORT` 确认端口释放。Step 5 输出报告，表格固定六列：接口、场景、期望、实际、对应测试、结论，末尾给出 Postman 集合状态和整体结论。Step 6 规定失败处理：任一项失败或缺测试就回到代码，先补失败测试再修，`make check` 通过后只重跑失败接口与相关场景；契约本身不合理时不得私自改契约，要按需求变更规则更新技术方案后再验证（契约冻结见「API 契约设计」）。

`1.0.0` 的实录按这套流程执行。`mktemp` 目录与端口 18090 启动真实进程，17 个场景全部通过：创建返回 201 与 `id` 格式、`title` 缺失 / 空白 / 101 字符、`content` 2001 字符、非法 JSON、未知字段、超 16 KiB、`PUT` 405、读取 200、404、大小写不匹配 404、`DELETE` 405、`healthz`、`ping`，以及 404 的 `message` 固定为 `note not found`。服务器日志不含笔记正文，对应需求「非功能需求」里「不记录笔记正文到日志」一条。结束后端口释放、运行目录删除。Postman 集合有 7 个请求：`healthz`、`ping`、`ping` 405、创建、读取、404、400；没有 Postman MCP，未使用。

## 可选独立审查：结论不替代命令

自验通过后，`ai-rules.md` 允许委派 Subagent `spec-reviewer`（`.claude/agents/spec-reviewer.md`，tools 仅 `Read, Grep, Glob`）按需求覆盖、实现正确性、生产风险三轮审查。`1.0.0` 第一轮 verdict 为 `changes_required`，5 条 finding。R1、R2 两条代码缺陷按 6.1 的规则「先补失败测试再修」处理，R3 到 R5 由主会话回写文档。第二轮 verdict `pass`，新增 R6 并修正，六条 finding 全部 `verified`，「交付状态」`review` 写成 `pass`。逐条 finding 的内容与修复方式见「Subagent 与 Hook 落地」。

R1 这条要单独说：改为返回 `note.ErrAlreadyExists` 而不覆盖，是严格满足需求「不得覆盖」，没有放宽需求，不需要用户来决定。审查结论不替代命令结果，修复后的候选重新跑了完整门禁，没有拿审查 `pass` 顶替。还有一点要如实说明：实现由通用 Agent 加载 `.claude/agents/spec-implementer.md` 正文扮演 `spec-implementer`，不是 Claude Code 原生 agents 目录加载；两个 Subagent 的原生加载与运行时工具限制都没有端到端记录（见「Subagent 与 Hook 落地」）。

## 6.2 用户验证：Postman 是可选工具，确认不是

6.2 第 1 步要求把自验结果展示给用户：各命令输出摘要、接口核对表、验收标准与测试对应表。第 2 步提示用户 `make run` 启动服务（默认 `:8080`），按任一方式验收。有 Postman MCP 时 AI 可代为运行 `api/postman/` 集合并展示结果，没有则用户手动导入集合；也可以直接使用 `api-verify` 报告中的 curl 命令。用户的反馈范围包括接口行为与预期不符、响应字段 / 状态码 / 错误信息偏差、性能或数据问题。

第 3 步是这一节的核心：用户验证不是可选步骤，Postman 只是可选工具；用户最终确认前，Step 6 不算完成，不得进入 Step 7。第 4 步把确认落到文件：用户明确确认后，把「交付状态」`user_acceptance` 改为 `confirmed`，启用 Graph 时随后执行 `event {version} verified`。

## 6.3 反馈修复循环怎样退出

用户反馈问题时，6.3 规定的顺序是先补一个复现该问题的失败测试（单元或集成），再改代码。然后只重跑受影响范围的自验：逻辑改动重跑 `make check` 与相关集成测试，接口改动重跑 `api-verify` 对应接口和 `make smoke`。复验后再次进入用户验证，可能经历多轮「反馈 -> 修改 -> 复验 -> 用户验证」。这与 Loop Engineering 的出口一致：每次修复从一个可观察失败出发，验证只扩大到相交范围，绿色不等于交付。

退出条件落在具体措辞上：只有用户明确表示「确认验证通过」「没有问题」「可以进入下一步」等最终确认，Step 6 才算完成。含糊的「看起来还行」不构成确认。还有一条分流规则：用户反馈属于新增需求或需求变更时，按「需求变更与新增规则」重新读需求、更新技术方案、经用户确认后再编码，不得当作 bug 直接改。

## 交付状态块把用户确认变成机器可核对的事实

用户的确认如果只留在会话记录里，下一个会话无法核对。模板把它放进 `Specs/technical/{version}/技术方案.md` 里唯一的「交付状态」块，位置在「文件清单」之后、「变更记录」之前。`1.0.0` 的内容是：

```yaml
stage: verifying             # planning | implementing | verifying | delivered
user_acceptance: pending     # pending | confirmed
review: pass                 # not_required | pending | changes_required | pass
```

三个键的变化点各有归属：用户确认方案后 `stage` 改 `implementing`，进入 Step 6 改 `verifying`，用户在 6.2 确认后 `user_acceptance` 改 `confirmed`，Step 7 回写完成后 `stage` 改 `delivered`；`review` 只有做了审查才离开 `not_required`。`internal/specdoc/delivery.go` 的 `ParseDeliveryStatus` 要求文档恰好有一个「## 交付状态」标题，围栏代码块内的引用不算，其后第一个代码块必须是 ```` ```yaml ````，只允许这三个键，重复键、未知键、未闭合围栏都报错。它不用 `bufio.Scanner`，超长行会让 `Scan` 静默失败并截断文档。解析后的 `Validate` 执行交付门禁：

```go
// internal/specdoc/delivery.go
	if d.Stage == "delivered" {
		if d.UserAcceptance != "confirmed" {
			return errors.New("stage 为 delivered 但 user_acceptance 不是 confirmed")
		}
		if d.Review != "pass" && d.Review != "not_required" {
			return fmt.Errorf("stage 为 delivered 但 review 为 %s", d.Review)
		}
	}
```

`internal/speccheck` 的 `checkPlan` 对每个版本的技术方案调用 `ParseDeliveryStatus`，错误直接成为 `spec-check` 的 problem，而 `spec-check` 是 `make check` 的一部分。一个未经用户确认就被改成 `delivered` 的版本，会让最基本的检查命令失败。Step 7 第 7 条写的「`spec-check` 会拒绝 `user_acceptance` 未 `confirmed` 或 `review` 为 `pending` / `changes_required` 的 delivered」就是这段代码。启用 Graph 时，`internal/specgraph/transition.go` 里 `verified` 事件的守卫也读同一个块，用户决定只记录在这一处，`graph.json` 不另存一份。计算 inputs 摘要时技术方案会先剔除「交付状态」块，把 `pending` 改成 `confirmed` 不会让已记录的证据失效。

## 1.0.0 现在停在哪里

| 位置 | 当前值 |
| --- | --- |
| 技术方案「交付状态」 | `stage: verifying`、`user_acceptance: pending`、`review: pass` |
| `graph.json` | stage `verifying`、revision 46 |
| `go run ./cmd/spec-graph status 1.0.0` | `invalidated: false`（运行时由 `internal/specgraph/check.go` 的 `Status` 计算，不写入 `graph.json`） |
| 最终门禁证据 | revision 42 到 46 记录的 check、test-integration、test-race、smoke、api-verify，均绑定候选 `2d03ec4f1c56` 与 inputs `1c1fd583b8f5`，退出码 0 |
| `go run ./cmd/spec-graph check 1.0.0` | 退出码 0 |
| `go run ./cmd/spec-graph event 1.0.0 verified` | 退出码 3 |

被拒绝的那条事件输出的是守卫消息：

```text
守卫不满足: verified: 技术方案「交付状态」user_acceptance 为 pending，需要 confirmed
```

`verified` 守卫在此之前已经检查过四类证据绑定当前候选与 inputs 摘要且退出码 0、`test-race` 证据退出码 0、所有 finding 为 `verified` 或 `rejected`。这些全部满足，唯一缺的是用户确认。Graph 与 Loop 的分工就落在这里：Loop 已经在每个 Case 上收敛，Graph 判断这些结论合起来是否足以推进阶段，用户确认是它读取的输入之一，它自己生成不出来（见「Spec + Graph 理论」与「Spec + Graph 落地」）。

用户确认后要做的三件事，顺序固定：

1. 把「交付状态」`user_acceptance` 改为 `confirmed`，再执行 `go run ./cmd/spec-graph event 1.0.0 verified`，阶段进入 `ready_to_deliver`。
2. 按 Step 7 回写技术方案、`技术讲解.md`、Postman 集合、`scripts/smoke.sh` 与 README，把「测试计划」定格为实际用例清单，然后把 `stage` 改为 `delivered`。
3. 运行 `make check` 与 `go run ./cmd/spec-graph check 1.0.0`：前者核对 `delivered` 的两个前提，后者核对 `delivered` 与 graph 阶段 `ready_to_deliver` 一致且未失效。

在此之前，`1.0.0` 的准确描述只有一句：自验与审查已完成，版本未交付，等待用户验收确认。命令能证明代码符合契约，只有用户能证明契约符合意图。模板不替用户做这个判断，它做的是让「判断还没做出」这件事，在文件和命令里都跳不过去。

# spec-graph 落地：CLI、graph.json 与 Subagent 编排

`cmd/spec-graph` 是版本生命周期状态图的薄 CLI。逻辑全部在 `internal/specgraph`：`graph.go`、`digest.go`、`store.go`、`transition.go`、`check.go`。状态落在 `Specs/technical/<version>/graph.json`。

这个 CLI 不运行任何命令。它记录阶段，把证据绑定到当时的 inputs 与 candidate 摘要，用守卫判断一个事件能不能发生。边界见 `理论.md`，工作流见 `.ai/skills/spec-graph-workflow/SKILL.md`。

## graph.json 字段

| 字段 | 含义 |
| --- | --- |
| `version` | 与目录名一致，不一致时读取直接拒绝 |
| `revision` | 每次成功写入加 1，`init` 为 0 |
| `stage` | `planning`、`implementing`、`reviewing`、`fixing`、`verifying`、`ready_to_deliver` |
| `inputs` | `files`（路径 -> sha256）与 `digest` |
| `candidate` | 同上 |
| `findings[]` | `id`、`severity`（P0..P3）、`status`、`note`、`updated_at` |
| `evidence[]` | `kind`、`candidate`、`inputs`、`exit_code`、`log_sha256`、`recorded_at`，只追加 |
| `events[]` | `id`、`type`、`from`、`to`、`revision`、`at` |

三个切片为空时输出 `[]`。时间统一为 UTC 秒精度带 `Z` 的 RFC3339。

## 摘要规则

- inputs：`Specs/requirements/<version>/需求.md`、`Specs/requirements/协议与数据.md`、`Specs/technical/<version>/技术方案.md`。
- candidate：`cmd`、`internal`、`scripts`、`api`、`migrations` 五个目录下的普通文件，加 `go.mod`、`go.sum`、`Makefile`。目录不存在跳过，`go.mod`、`go.sum` 缺失不算，`Makefile` 必须是普通文件；以 `.` 开头的目录与文件跳过，符号链接不跟随。
- `digest`：路径排序后按「路径\n摘要\n」拼接再取 sha256。
- 技术方案有一处例外：先剔除「## 交付状态」标题到其后第一个代码块结束的内容，再算摘要。
- 每次成功写入都把重算出的两个摘要回写到顶层，`status` 的漂移相对上一次写入。

交付状态块记录的是用户决定，守卫直接读它。它变化不算需求漂移，也不算方案漂移。用 `shasum` 手工核对技术方案时先剔掉这一块，否则数字对不上。

## 命令速查表

| 命令 | 作用 | 备注 |
| --- | --- | --- |
| `spec-graph [--root <dir>] init <version>` | 创建 graph.json，阶段 `planning` | 已存在退出 3 |
| `status <version> [--json]` | 只读；重算摘要，输出阶段、漂移、finding 计数、各 kind 最新证据、交付状态 | 文本模式摘要只显示前 12 位 |
| `record <version> --kind <k> --exit <n> [--log <path>] [--expect-revision <n>]` | 追加一条证据并绑定此刻摘要 | kind 限 `check`、`test-integration`、`test-race`、`smoke`、`api-verify`、`review`；`--log` 取文件 sha256 |
| `finding <version> --id <id> --severity <P0..P3> --status <s> [--note <text>] [--expect-revision <n>]` | 新建或推进 finding | 新建必须 `open`；流为 `open -> accepted` 或 `rejected`、`accepted -> fixed`、`fixed -> verified` |
| `event <version> <type> [--id <id>] [--expect-revision <n>] [--at <RFC3339>]` | 推进阶段，守卫在锁内判定 | `--at` 只改写事件时间 |
| `check <version>` | 只读核对 graph 与技术方案交付状态 | 有问题按 `路径: 消息` 打印并退出 1 |

`--root` 只在子命令之前解析。版本号必须形如 `x.y.z`。写入命令成功时打印 `stage=<stage> revision=<n>`。

## 退出码

| 退出码 | 触发条件 |
| --- | --- |
| 0 | 成功；`check` 无问题 |
| 1 | `check` 报告问题；graph.json 不存在；其他读写或解析错误 |
| 2 | 用法错误：子命令、版本号、事件类型、`--kind`、`--severity`、`--status` 不合法，缺少必填 flag，多余参数，`--log` 读不到 |
| 3 | 守卫拒绝（非法转换、守卫不满足、finding 流不允许、新 finding 非 `open`）；冲突（锁被占用、`--expect-revision` 不符、事件 `--id` 类型冲突、自动 id 被占、`init` 时文件已存在） |

## 写入与读取规则

- 锁：`record`、`finding`、`event` 用 `O_CREATE|O_EXCL` 独占创建 `graph.json.lock`，覆盖 load 到 commit 的全程。锁已存在就退出 3，并打印它的创建时间。`SIGINT`、`SIGKILL` 打断会留下残锁，`check` 会报出来；确认没有进程在跑之后手工删掉。
- `--expect-revision`：读完之后比较，不符退出 3。它防不住丢写，防丢写的是锁。
- 落盘：先 `validateState`，在同目录写 `graph.json.tmp-*`（0644）并 `fsync`。`init` 用 `os.Link` 独占创建，文件系统不支持硬链接时退回 rename，其余情况 rename 覆盖。失败就删掉临时文件。
- 读取：拒绝首个 JSON 值之后的多余内容与重复键，`DisallowUnknownFields`，校验 version、枚举、时间格式与 id 唯一，再把事件序列从 `planning` 重放到记录的 `stage`。不要手工编辑 graph.json。
- 幂等：`event --id` 同 id 同类型返回成功但不写盘，同 id 不同类型退出 3；不给 `--id` 时自动生成 `evt-<revision>`，被占用退出 3。`finding` 同 id 相同 `--status` 幂等成功，不改 severity 与 note；合法转换不带 `--note` 时保留原 note。

## 事件守卫表

守卫读三类输入：技术方案里的「交付状态」，即用户决定；graph.json 里带摘要的证据；finding 状态。

「绑定」有精确含义：该 kind 的最后一条证据 `exit_code=0`，且它的 `candidate` 等于当前重算的摘要。部分事件还要求 `inputs` 相等。

| 事件 | from -> to | 守卫 |
| --- | --- | --- |
| `plan_confirmed` | `planning` -> `implementing` | 交付状态 `stage` 不再是 `planning` |
| `implementation_done` | `implementing` -> `reviewing` | `check` 绑定当前 candidate 与 inputs |
| `review_failed` | `reviewing` -> `fixing` | 存在 `open` 或 `accepted` 的 finding |
| `review_passed` | `reviewing` -> `verifying` | 无 `open`、`accepted`、`fixed` finding；`review` 绑定当前 candidate（不要求 inputs） |
| `fix_done` | `fixing` -> `reviewing` | 无 `open` finding；`check` 绑定当前 candidate 与 inputs |
| `verified` | `verifying` -> `ready_to_deliver` | `check`、`test-integration`、`smoke`、`api-verify` 都绑定当前 candidate 与 inputs；`test-race` 若有记录须 `exit_code=0`；所有 finding 为 `verified` 或 `rejected`；交付状态 `user_acceptance` 为 `confirmed` |
| `readiness_invalidated` | `verifying` 或 `ready_to_deliver` -> `fixing` | `invalidated` 为真 |

`invalidated` 为真的条件：stage 是 `reviewing`、`verifying`、`ready_to_deliver` 之一，并且 inputs 或 candidate 摘要与上一次写入不同。

## check 的规则

`check` 按固定顺序报告：

1. graph.json 解析或校验失败。
2. 锁文件残留。
3. 有 graph.json 但缺技术方案。
4. 摘要无法计算。
5. stage 为 `ready_to_deliver` 且已失效，该执行 `readiness_invalidated`。
6. 交付状态无法解析。
7. 交付状态 `delivered`，但 graph 不在 `ready_to_deliver` 或已失效。
8. graph 已 `ready_to_deliver`，但 `user_acceptance` 不是 `confirmed`。

`ready_to_deliver` 不是交付。交付由交付状态的 `delivered` 表示，两者必须一致。

## 工作流 Step A 到 E

| Step | Controller（主会话，唯一执行者） | 委派 |
| --- | --- | --- |
| A | 用户确认方案后交付状态 `stage` 改 `implementing`；`init`；`event plan_confirmed` | 无 |
| B | 按文件清单与 Feature 切片；收回 YAML；运行 `make check` 并 `record --kind check`；`event implementation_done` | `spec-implementer`，只跑 focused 测试，互不重叠的切片可并行 |
| C | 逐条 `finding --status open`，判断 `accepted` / `rejected`（需求取舍先问用户）；`record --kind review`（pass 为 0，changes_required 为 1）；`review_failed` -> 修复 -> `fixed` -> `make check` 并 `record` -> `fix_done` -> 再审 -> `verified`；无阻塞时 `review_passed` 并把交付状态 `review` 写 `pass` | `spec-reviewer` 只读，返回 verdict 与 findings |
| D | 依次运行 `make test-integration`、`make test-race`（有并发改动）、`make smoke`、Skill `api-verify` 并逐项 `record`；交付状态 `stage` 改 `verifying`；用户确认后 `user_acceptance: confirmed`；`event verified` | 无 |
| E | Step 7 回写；交付状态改 `delivered`；`make check` 与 `spec-graph check`。之后任何改动使 `invalidated: true`，执行 `readiness_invalidated` 回到 `fixing`，交付状态改回 `implementing`，重走 B 到 D | 无 |

record 有一条诚实义务。CLI 无法知道 `--exit` 是不是来自真实运行，退出码必须来自 Controller 刚跑完的那条命令，`--log` 指向它的输出。

Implementer 不跑 broad 门禁，不改 `Specs/requirements/**`、`graph.json`、`.ai/skills/go-development/**`。Reviewer 不改任何文件。Subagent 的结论不替代命令结果。

Codex 没有 Subagent。那边可以只用 CLI 记录状态，实现与审查在同一会话里串行做完。

## 1.0.0 实录

`Specs/technical/1.0.0/graph.json`：revision 46，stage `verifying`，`invalidated: false`。事件为 `evt-1` `plan_confirmed`、`evt-3` `implementation_done`、`evt-14` `review_failed`、`evt-26` `fix_done`、`evt-41` `review_passed`。

第一轮审查 `changes_required`，开出 R1 到 R5，候选 `04a68378d8b4`。修复后候选换成 `2d03ec4f1c56`，第二轮 `pass`，新增 R6。六条 finding 最后都是 `verified`。

revision 27 到 30 的证据绑定的 inputs 是 `e5636895cabd`。R6 的修正动了技术方案，inputs 变成 `1c1fd583b8f5`，42 到 46 在同一候选上把五类门禁重新记了一遍。

`check 1.0.0` 退出 0。`event 1.0.0 verified` 被拒绝，退出 3：

```text
守卫不满足: verified: 技术方案「交付状态」user_acceptance 为 pending，需要 confirmed
```

交付状态为 `stage: verifying`、`user_acceptance: pending`、`review: pass`。版本未交付，等用户验收。

1.0.0 演示里的 `spec-implementer`、`spec-reviewer` 由通用 Agent 加载定义文件正文扮演，不是 Claude Code 原生 agents 目录加载，`tools` 的运行时限制没有端到端记录。Graph 只认摘要、退出码与交付状态，不依赖这一点。

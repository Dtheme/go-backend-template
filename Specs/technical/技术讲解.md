# 技术讲解

> 项目技术全景，由 AI 维护并始终与代码保持一致。版本开发结束（Step 7）和日常修改后都要更新本文件。

## 项目概述

- 服务名称：go-backend-template
- 描述：最小生产级 Go 后端模板工程，提供 HTTP 服务骨架、配置、日志、优雅停机、统一错误响应、本地验证工具链，以及 Spec 一致性检查（`spec-check`）与可选的版本生命周期状态图（`spec-graph`）
- 架构：入口（cmd）→ HTTP 层（httpapi）→ 业务层（`internal/note`）← 存储层（`internal/memstore`，内存实现）
- Go 版本：module 声明 `go 1.25.0`
- 第三方依赖：无，仅标准库
- 对外接口：`GET /healthz`、`GET /v1/ping`、`POST /v1/notes`、`GET /v1/notes/{id}`（1.0.0）

## 核心模块

### 入口与生命周期（cmd/api）

1. 创建 `slog` JSON logger，输出到 stdout
2. `config.Load()` 读取环境变量
3. 构建 `http.Server`，设置 `ReadHeaderTimeout` 5s、`ReadTimeout` 10s、`WriteTimeout` 10s、`IdleTimeout` 60s
4. goroutine 中 `ListenAndServe`，主 goroutine 监听 `SIGINT` / `SIGTERM`
5. 收到信号后在 `SHUTDOWN_TIMEOUT` 内 `Shutdown`，让在途请求完成；监听失败或停机失败以退出码 1 结束

### 配置（internal/config）

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `HTTP_ADDR` | `:8080` | 监听地址 |
| `SHUTDOWN_TIMEOUT` | `10s` | 优雅停机超时，非法值回退默认 |

新增配置项时在 `Config` 加字段、`Load` 加解析、`config_test.go` 补默认值与覆盖用例，并同步本表和 README。

### HTTP 层（internal/httpapi）

- 路由：`http.ServeMux` + `METHOD /path` 模式；未匹配路径返回 404，方法不匹配返回 405（`ServeMux` 默认文本响应）
- 中间件顺序：`withRecover` 在最外层，`withRequestLog` 其次，最后是 `mux`
- `writeJSON(w, status, body)`：设置 JSON Content-Type 并编码
- `writeError(w, status, code, message)`：写入 `{"error":{"code","message"}}` 信封；错误码取值见 `Specs/requirements/协议与数据.md`
- 请求日志字段：`method`、`path`、`status`、`duration_ms`；不记录请求体与敏感 header
- 笔记接口（`notes.go`）：`decodeJSON` 用 `http.MaxBytesReader` 限制 16 KiB、`DisallowUnknownFields`、并拒绝首个 JSON 值后的尾随数据；`*note.ValidationError` -> 400 `invalid_argument`（message 为校验信息），`note.ErrNotFound` -> 404 `not_found`，其他错误 -> 500 `internal_error` 并记录日志

### 业务层（internal/note）与存储层（internal/memstore）

- `note.Service`：`Create` 去掉 title 首尾空白，按 `utf8.RuneCountInString` 校验 title 1–100、content ≤ 2000（超限返回 `*ValidationError`，message 指明字段），用 `crypto/rand` 生成 `n_` + 12 位小写十六进制 ID，`created_at` 为 UTC；`Get` 未找到返回 `ErrNotFound`
- `note.Repository`：`Save(ctx, Note) error`、`Find(ctx, id) (Note, bool, error)`；`Save` 遇到已存在 ID 返回 `ErrAlreadyExists`
- `memstore.Store`：`sync.RWMutex` 保护的 `map[string]note.Note`；数据只在进程内存中，重启丢失（1.0.0 演示范围）
- 依赖方向 `cmd -> httpapi -> note <- memstore`；新增领域按同样方式建 `internal/{domain}/` 与 `internal/{storage}/`（如 `internal/postgres/`）

### 工程工具（cmd/spec-check、cmd/spec-graph、internal/specdoc）

**specdoc**：`ParseDeliveryStatus` 要求技术方案恰好有一个「## 交付状态」标题（围栏代码块内不算），其后第一个代码块必须是 yaml 围栏，只含 `stage` / `user_acceptance` / `review` 三个键；`Validate` 校验枚举并执行门禁：`stage: delivered` 要求 `user_acceptance: confirmed` 且 `review` 为 `pass` 或 `not_required`。按行切分不用 `bufio.Scanner`，超长行不会被截断。

**spec-check**（`make check` 的一部分，`speccheck.Run(root)` 返回按路径排序的问题列表）：

| 规则 | 检查 |
| --- | --- |
| 1 | 需求模版、协议与数据、技术讲解、技术方案模版、ai-rules.md、Makefile 存在且为普通文件 |
| 2 | ai-rules.md 的「文件权限规则」「AI 工作流（版本开发）」「验证命令」二级标题各恰好一次（围栏内不计） |
| 3 | 技术讲解含「目录结构」「接口清单」「测试策略」「已知问题与待优化项」 |
| 4 | CLAUDE.md、AGENTS.md、.claude/skills、.agents/skills 是符号链接、readlink 逐字相等、目标存在 |
| 5 | Specs 两侧版本目录名匹配 x.y.z；requirements 有版本必须有对应技术方案（提示 `make spec-init`），反之亦然 |
| 6 | 需求中的 `F-<v>-NNN` 至少一个、版本段与目录一致、每个都出现在技术方案；技术方案不得引用其他版本的 ID |
| 7 | 技术方案八个二级标题（需求摘要、API 契约、模块设计、测试计划、风险与回滚、文件清单、交付状态、变更记录）各恰好一次 |
| 8 | 「交付状态」块能被 specdoc 解析且通过门禁 |
| 9 | `api/postman/*.postman_collection.json` 是 JSON 对象，`info.name` 非空字符串，`item` 为数组 |
| 10 | 版本目录内只允许 需求.md / 技术方案.md、graph.json 与点文件 |

退出码：0 无问题（输出 `spec-check ok (N version(s))`）、1 有问题（每行一个 `路径: 问题`）、2 I/O 错误。

**spec-graph**（可选，`specgraph.Graph{Root, Version}`）：状态文件 `Specs/technical/{version}/graph.json` 记录 `stage`、`revision`、`inputs` 与 `candidate` 摘要、`findings`、`evidence`、`events`。摘要规则：inputs 为需求、协议与数据、技术方案三个文件，其中技术方案剔除「交付状态」块后再摘要（改交付状态不算输入变化）；candidate 为 `cmd`、`internal`、`scripts`、`api`、`migrations` 下全部普通文件加 `go.mod`、`go.sum`、`Makefile`（跳过点文件与 `.DS_Store`）。六个阶段与七类事件的守卫见 `docs/spec-graph/落地.md`；`invalidated` 由当前摘要与记录摘要比较派生，不持久化。写入在 `graph.json.lock` 独占锁内完成（被占用时退出码 3），先写同目录临时文件、fsync、rename；读取用 `DisallowUnknownFields` 并从 `planning` 重放事件核对 `stage`。退出码：0 成功、1 check 有问题或未初始化、2 用法错误、3 守卫拒绝或 revision / 锁冲突。

## 关键设计约定

| 约定 | 位置 |
| --- | --- |
| 标准库优先，新增第三方依赖需先告知用户 | `.ai/ai-rules.md` |
| 文档一致性由 `spec-check` 机器核对，交付状态块是唯一机器可读的用户决定记录 | `internal/speccheck`、`internal/specdoc`、`Specs/technical/技术方案模版.md` |
| Graph 只记录执行阶段与证据身份，不运行命令、不另存完成真相 | `internal/specgraph`、`.ai/skills/spec-graph-workflow/SKILL.md` |
| 错误统一信封，内部错误不泄露细节 | `internal/httpapi/response.go` |
| 日志结构化（slog），不记录敏感信息 | `cmd/api/main.go`、`middleware.go` |
| 配置只来自环境变量，无配置文件 | `internal/config` |

## 已知问题与待优化项

- 404 / 405 由 `ServeMux` 返回纯文本，未使用 JSON 错误信封；需要统一时在 `NewHandler` 中包一层 fallback handler
- 尚无 `/readyz`；引入数据库等外部依赖后补充
- `spec-graph` 的锁是同目录文件锁，只防止两个进程同时写；不判定锁的归属，进程被中断后残留的锁由 `check` 报告、人工确认后删除
- `spec-graph record` 的退出码由 Controller 提供，工具不重跑命令核实；证据可信度取决于 Controller 只记录刚运行的命令结果
